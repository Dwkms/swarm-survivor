# 성능 측정 기록

풀링 전후를 비교하려면 **같은 조건에서 잰 값**이어야 합니다. 이 문서는 측정치와 함께
**그때의 조건**, 그리고 **폐기한 결론**을 남깁니다. 폐기한 것을 지우지 않는 이유는, 판단이
어떻게 바뀌었는지가 이 프로젝트의 산출물이기 때문입니다.

## 기록 규칙

| 항목 | 이유 |
|---|---|
| **측정 위치 — 에디터 / 빌드** | 에디터에서는 EditorLoop가 프레임 시간의 86%를 차지했습니다. **기준선은 빌드에서 잽니다** |
| **플레이어 이동 여부** | 900마리 기준 정지 2.30ms, 이동 6.89ms |
| **적 마릿수** | 다른 마릿수의 측정치로 결론을 검증할 수 없습니다 |
| **읽는 값** | `AVG`(F4 리셋 이후 누적)와 `worst`. **`now`(0.5초 창)는 참고용** |
| **BulletWeapon ON/OFF** | 켜져 있으면 적이 죽어 마릿수가 계속 줄어듭니다 |
| **스폰 중인지 아닌지** | 스폰 스파이크가 섞이면 마릿수의 비용이 아닙니다 |
| **대기 시간** | 적이 도달하는 데 반경 14 ÷ 속도 2 = **7초**. 최소 12초 대기 |
| **VSync** | 켜져 있으면 주사율에 묶여 여유가 얼마나 남았는지 알 수 없습니다 |
| **PC** (데스크탑 / 노트북) | 다른 PC의 전·후 수치는 비교할 수 없습니다 |
| 렌더 조건 | 무텍스처 컬러 사각형 · 단일 머티리얼 |

**지표는 FPS가 아니라 프레임 시간(ms)입니다.** FPS는 비선형이고 평균은 스파이크를 감춥니다.
60fps 기준선 = **16.67ms**

## 부하 3종 분류 — 이 프로젝트의 핵심 논지

| 부하 | 정의 | 빌드 실측 (900마리) | 오브젝트 풀링이 개선하는가 |
|---|---|---|---|
| 존재 | 씬에 있는 것만으로 드는 비용 | 2.30ms | 아니다 |
| **이동** | 활성 오브젝트가 매 프레임 물리로 움직이는 비용 | AVG 6.89ms / **worst 68.73ms** | **아니다** |
| 생성·파괴 | `Instantiate`/`Destroy` 자체 비용 | 100개 동시 1.28~5.02ms, **GC 0KB** | **그렇다** |

**가장 큰 비용은 풀링이 고치는 곳이 아닙니다.** 이 사실을 감추지 않고 그대로 보고하는 것이
이 프로젝트의 결론입니다.

## 2026-09-01 · 수면 가설 검증 → 기각

임시 진단 스크립트 `SleepProbe`(`F2`)로 수면 마릿수와 평균 속도를 직접 셌습니다.

**조건** — 에디터 / 적 100마리 / `BulletWeapon` OFF / `spawnsPerSecond` 0

| 시점 | 마릿수 | 수면 | 활성 | 평균 속도 |
|---|---|---|---|---|
| 정지 12초 | 100 | 11 (11%) | 89 | 1.780 |
| 이동 중 | 100 | 0 | 100 | 2.000 |

**정지 상태에서도 89%가 깨어 있고 속도 2.000을 유지합니다.** 적 Collider가 Trigger라
플레이어에게 막히지 않으므로, 적은 목표에 도달하는 것이 아니라 **통과한 뒤 되돌아오며
무한히 진동합니다.** 속도가 0이 되지 않으니 잠들지 않습니다.

**수면으로는 차이를 설명할 수 없습니다. 가설 기각.**

### 이날 배운 측정 오염 2건

1. `BulletWeapon`이 켜져 있어 적이 죽으며 마릿수가 100 → 87로 줄었습니다
2. 적 도달 시간(7초)보다 짧게 기다려 측정했습니다. 최소 12초 대기

## 2026-09-02 · 에디터 측정의 함정 — EditorLoop 86%

Profiler로 프레임 내부를 열어봤습니다.

**평범한 프레임(CPU 11.95ms) 하나의 내역**

| 항목 | Total | Time ms |
|---|---|---|
| **EditorLoop** | **86.4%** | **10.33ms** |
| PlayerLoop | 11.1% | **1.32ms** |

**실제 게임은 1.32ms고 나머지는 전부 에디터가 자기 창을 그리는 비용이었습니다.**
Scene 뷰 렌더링, Inspector·Hierarchy 갱신, Profiler 창 그리기가 모두 포함됩니다.

`Time.unscaledDeltaTime`은 에디터 프레임 전체를 재므로, `PerfMonitor`가 표시한 값은
처음부터 `게임 비용 + 에디터 비용`이었습니다.

**결론 — 에디터에서 잰 절대값은 기준선으로 쓸 수 없습니다. 빌드에서 다시 쟀습니다.**

## 2026-09-02 · 측정 도구 자체의 결함과 수정

첫 곡선 측정에서 600마리(0.82ms)가 400마리(2.19ms)보다 낮게 나오는 역전이 생겼습니다.

원인은 `PerfMonitor`가 표시하던 값이 **직전 0.5초 창의 평균**이었다는 것입니다.
눈으로 읽는 시점이 스파이크 직전이냐 직후냐에 따라 값이 크게 달라집니다.

**수정** — `F4` 리셋 이후 모든 프레임을 누적하는 `AVG`를 추가했습니다.
`worst`와 같은 기준으로 맞춰져 이제 두 값을 함께 읽을 수 있습니다.
`now`(0.5초 창)는 참고용으로만 둡니다.

**측정 도구를 신뢰하기 전에 도구를 검증해야 한다는 것을 이 역전이 알려줬습니다.**

## 2026-09-02 · 빌드 기준선 (유효한 기준선)

**조건** — Windows 빌드 / **non-development** / **VSync OFF** / 데스크탑 /
`BulletWeapon` OFF / `spawnsPerSecond` 0 / 스폰 후 12초 대기 / `F4` 리셋 후 이동 10초

### 생성 부하 — 풀링 비교의 기준선

| 시점 | 프레임 시간 | GC Alloc |
|---|---|---|
| `F1` #1 (0 → 100마리) | **5.02ms** | 0 KB |
| `F1` #9 (800 → 900마리) | **1.28ms** | 0 KB |

**첫 생성이 4배 비쌉니다.** 프리팹 최초 로드와 머티리얼·셰이더 워밍업 같은 일회성 비용이
첫 프레임에 몰립니다. **풀링 전후를 비교할 때는 워밍업 이후 값으로 맞춰야 공정합니다.**

**GC Alloc이 0입니다.** Unity의 GameObject·Component는 대부분 네이티브 메모리에 잡히고
관리 힙은 거의 늘지 않습니다. 따라서 **"풀링으로 GC를 줄인다"는 서사는 이 프로젝트에서
성립하지 않습니다.** 풀링이 없애는 것은 GC가 아니라 네이티브 할당과 컴포넌트 초기화 비용입니다.

### 이동 중 마릿수 곡선

| 적 마릿수 | AVG | worst | worst / AVG |
|---|---|---|---|
| 200 | 1.38ms | 5.05ms | 3.7배 |
| 400 | 1.75ms | **14.89ms** | 8.5배 |
| 600 | 2.55ms | **31.24ms** | 12.2배 |
| 900 | 6.89ms | **68.73ms** | 10.0배 |

**정지 상태 참고** — 900마리 IDLE은 AVG 2.30ms / worst 25.88ms입니다.

### 해석

**1. 평균은 900마리에서도 여유가 있습니다.** 6.89ms는 145fps입니다. 문제는 평균이 아닙니다.

**2. 스파이크가 평균의 10배입니다.** 400마리부터 `worst`가 `AVG`의 8~12배로 벌어집니다.
이것이 체감 버벅임의 정체입니다.

**3. 비용이 마릿수에 선형이 아닙니다.**

```
마릿수   200 → 900    4.5배
worst   5.05 → 68.73  13.6배     →  대략 n^1.7
```

오브젝트 하나당 드는 비용이라면 정확히 4.5배여야 합니다. 초선형이라는 것은
**비용이 오브젝트 개수가 아니라 오브젝트 쌍(pair)에서 나온다**는 뜻이며,
물리 브로드페이즈 가설과 맞는 모양입니다.

### 스펙 판정

**`worst`가 60fps 기준선 16.67ms를 넘는 지점은 400~600 사이, 약 430마리입니다.**

게임 스펙의 활성 상한 400은 그 바로 아래이고, 14.89ms로 **여유가 11%입니다.**
아슬아슬하지만 400은 상한이지 상시 상태가 아닙니다. 실제 플레이에서는 총알이 계속 죽이므로
동시 활성이 400에 닿는 일은 드뭅니다. **스펙은 유지합니다.**

### 이동 부하의 원인 — 유력 가설 (미검증)

Box2D는 각 Collider의 AABB를 실제보다 크게(fat AABB) 만들어 트리에 넣고, 오브젝트가 그
여유 범위를 벗어날 때만 트리에서 빼고 다시 넣습니다.

| 상태 | 적의 움직임 | 브로드페이즈 트리 |
|---|---|---|
| IDLE | 플레이어를 통과했다 되돌아오며 제자리 진동 | 여유 범위 안. **갱신 거의 없음** |
| MOVING | 플레이어를 쫓아 한 방향으로 계속 이동 | **매번 범위 이탈. 재삽입** |

비용을 만드는 것은 겹침의 개수가 아니라 **움직임의 방향성**이라는 설명입니다.
초선형 증가도 이 가설과 어긋나지 않습니다. 다만 검증은 하지 못했습니다.

## 참고 · 스펙대로 플레이하면 부하가 얼마나 되나

```
0~1분   초당 4  × 60초  =   240마리
1~3분   초당 8  × 120초 =   960마리
3~5분   초당 14 × 120초 = 1,680마리
                          ─────────
                          2,880마리
```

투사체와 EXP 젬까지 더하면 5분 통틀어 **6,000개 남짓, 초당 평균 20개** 수준입니다.
**초당 20개의 생성·파괴는 부하가 아닙니다.**

그래서 이 프로젝트의 주장은 "풀링 덕분에 게임이 돌아간다"가 아닙니다.
`Instantiate`/`Destroy` 방식의 비용을 측정으로 특정하고, 풀링이 그중 무엇을 얼마나
줄이는지를 **과장 없이 한정해서** 보이는 것입니다.
